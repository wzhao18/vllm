# P-MLA findings (prefill sparse MLA + prologue, DEP16, 96 heads/GPU)

- 2026-11-18 13:05 Standalone stock chain per layer at F16K (3 x 5,461 tok @ L78K, 1 GPU, runs/P-MLA/run1): trtllm-gen sparse MLA 2129.5 us (3.29 PF on real heads), w_uk bmm+RoPE copy 273.9, scaled_fp8_quant 204.1, _pad_query_heads 173.4, w_uv bmm 155.9, gate_sigmoid_mul 128.8, concat_and_cache_mla 42.0. In-family (attn + quant + pad + gate + insert) = 2677.8 us/layer = 64.3 ms/step (status baseline 67 ms from in-step F8K x2 agrees).
- 2026-11-18 13:05 FlashInfer prims_ts sparse MLA (image FI 0.7.3.dev20261031) refuses sm_107 ("sparse TS MLA requires SM100 or SM103"): not a usable alternative on VR in this image.
- 2026-11-18 13:05 tcgen05 operand-fetch probe (runs/P-MLA/run2/mma_rate.json): FP8 kind::f8f6f4 with the 2x-K bit reaches the full FP8 MMA rate when A comes from TMEM (any N >= 64, B K- or MN-major); with both operands in SMEM the MMA is capped by a fixed SMEM operand-fetch rate (measured 128 B/clk/SM in every ss row: N=96 gives 43% of peak, N=128 50%, N=256 67%). Design consequence: a sparse-MLA kernel must keep Q and P in TMEM (A operands) and read only K/V from SMEM; the keys-on-M (transposed) form with Q^T/P^T as SMEM B operands is capped near 43% and is ruled out.
- 2026-11-18 13:05 SMEM floor of any per-token sparse MLA: each 576 B KV row must be read from SMEM at least once for QK and once for PV (512 B) per 96 useful heads -> at most 77% of the FP8 MMA rate on real heads, which is about the perf model's achievable (76%). A 96->128 padded M=128 MMA with A in TMEM sits exactly on that floor, so padding costs nothing extra once SMEM-bound.
- 2026-11-18 13:05 TMEM is the binding constraint for the standard (heads-on-M) form: Q as A (144 cols) + O 128x512 FP32 (512 cols) + S/P already exceeds the 576-column exclusive allocation. The stock kernel resolves this by splitting V512 across a CTA pair (HVPerCta256) and recomputing QK in both CTAs; QK recompute plus head padding explain most of its 3.3x (code-level inference, ncu not available in the image: /usr/local/cuda/bin has no ncu/nsys).
- 2026-11-18 13:05 Gather floor with plain LDG (Triton, random 576 B rows, 3 requests x 45 MB KV, runs/P-MLA/run2): 18.2 TB/s -> 1064 us per F16K layer, 1.65x the model's sparse_mla achievable (643 us). The model counts only unique KV bytes (135 MB/layer) and omits the 19.3 GB/layer of per-token L2->SM row gathers. TMA gather4 floor being measured (run3); if it stays near 18 TB/s the model's DSA.sparse_mla row is a model error (gather traffic missing).
- 2026-11-18 13:40 TMA gather4 floor with more issuing warps (runs/P-MLA/run4): 8 warps 14.6 TB/s, 16 warps 17.6 TB/s (2-3 stages of 72 KB make no difference) -> the random 576 B row gather from L2 saturates at ~18 TB/s on VR200 for this access pattern (LDG gives the same 18.2). At F16K a layer gathers 19.3 GB -> ~1.07 ms floor for any kernel that reads each top-k row once per token, 1.67x the model's sparse_mla achievable (643 us). Model fix: add a per-token gather term F x 2048 x 576 B / ~18 TB/s to DSA.sparse_mla (and the decode equivalent). The stock trtllm-gen kernel at 2.13 ms matches ~2x this floor, consistent with its V half being re-gathered per CTA (FlashMLA's documented layout) (inference).
- 2026-11-18 13:45 Correction to the 13:05 entries: with the gather floor at ~1.07 ms/layer (F16K), the keys-on-M form's SMEM operand-fetch cap (~0.97 ms/layer: 238 KB of operand reads per 128-key tile at 128 B/clk/SM) sits just below it, so that form is viable (no head padding, no CTA pairs, S^T + O^T fit 512 TMEM columns). The stock kernel's 2.1 ms is better explained by ~2x gather bytes than by QK recompute (both are inferences without ncu). Building that form first (vllm/models/kimi_k3/nvidia/specialized_prefill/sparse_mla.py, ported from the GB300 T96 v2 prototype to dense 2x-K FP8 MMAs and per-tensor FP8 Q).
- 2026-11-18 14:00 Die-local KV check (runs/P-MLA/run5): gather4 (16 warps) from a KV pool homed entirely on die 0 vs the default striped pool: 17.5 vs 17.5 TB/s, and die-0 vs die-1 CTAs take the same time (1.05 ms) in both. Consistent with hwdb (a die caches remote-homed lines in its own L2): per-request KV (45 MB) is L2-resident on both dies, so die-local KV placement does not move the P-MLA gather floor; no placement work planned for P-MLA (directive 2026-11-18 checked with a measurement).
- 2026-11-18 14:00 One-kernel concat+quant+pad (decode_query_quant_pad, Triton) is slower than the two stock passes at 16K rows (422 us vs 204 + 174), so the fused query only saves the RoPE copy (net -10 us/layer on the stock path). With the specialized kernel (no head pad) the in-place concat + scaled_fp8_quant path is kept (477 us/layer: w_uk 273 + quant 204).
- 2026-11-18 14:00 First specialized kernel timing (run7, cp.async row loaders from the GB300 T96 v2 prototype): 5.8-6.9 ms per F16K layer, 2.8x slower than stock trtllm-gen (2.08 ms): loader-bound at ~6 B/clk/SM. Switched the loaders to TMA tile::gather4 (run8 pending). (run7's correctness numbers compared against a different layer's stock output: invalid, fixed.)
- 2026-11-18 14:05 Specialized keys-on-M kernel (specialized_prefill/sparse_mla.py, branch db27679958): correct on VR200 (5/5 tests: FP32 reference rel mean <2%, error <= 1.25x trtllm-gen's), but 4.6 ms per F16K layer at a realistic logit scale with (P_PRE, THR) = (4, 4.5) vs 2.08 ms stock (5.7 ms with (7, 1): the lazy-max slow path with O^T rescale costs ~20%). Pipelining softmax(t+1) with PV(t) and TMA gather4 loaders did not help (5.5-9.2 ms): the per-tile chain (~8.8K clk vs ~2.6K gather-bound target) is not loader issue rate. Leading hypothesis (from the GB300 T96 analysis, unmeasured on VR): with 2 KV stages each held QK -> softmax -> PV only one tile of gathers is in flight, exposing L2 latency; next step is a clock64 phase trace, then 3+ stages (oversized SMEM) or K/V split release. Dispatch stays off until it beats trtllm-gen.
