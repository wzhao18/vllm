# HW findings (public-safe: features only, no internal numbers; details in the private hwdb)

- 2026-11-18 Mixed MXFP8-activation x MXFP4-weight block-scaled MMA runs at the FP8 tensor rate on VR200; only FP4 x FP4 (NVFP4 or MXFP4 W4A4) reaches the FP4 rate. The NVFP4 checkpoint's routed experts can use it; the in-tree W4A8 MegaMoE path cannot. Matters for compute-bound prefill MoE, not for weight-bound decode.
- 2026-11-18 The Rubin double-K block-scaled MMA forms are selected by instruction-descriptor bits and only exist in sm_107a builds; family/sm_100f builds run the Blackwell form at half the block-scaled rate. Library MXFP8 and NVFP4 GEMMs we measured must already use the native form (their measured rate exceeds the Blackwell-form ceiling).
- 2026-11-18 Model observation: decode expert rows assume die-local HBM bandwidth (a non-localized MoE kernel cannot reach model achievable); dense decode GEMM rows assume the default striped rate (die-localizing dense weights can beat model achievable).
- 2026-11-18 Model observation: the prefill indexer-score row is costed near the Blackwell-form FP8 rate; a native sm_107a kernel (FP4 x FP4 or mixed at the FP8 rate) can go below model achievable. Flagged to P-IDX.
- 2026-11-18 Counted TMA stores signal completion at the destination (byte counter), removing the producer system fence + flag; payload and counter must share one large page or the count is silently skipped.
- 2026-11-18 Cluster launch control works on sm_107a, but for small decode work static/one-shot persistent scheduling was faster in internal measurements.
- 2026-11-18 Measured (Rhea): die-local HBM read is about 1.44x the default striped allocation and about 7% above the perf model die-local achievable rate (model is conservative for die-localized streams); all-remote is about half of striped.
- 2026-11-18 Measured: FP32 packed FMA (f32x2) has the same peak as scalar FFMA - it halves instruction count only; legacy warp-level BF16 mma.sync runs at one quarter of the tcgen05 BF16 rate (recurrences on mma.sync are capped there).
- 2026-11-18 Measured: a VR200 die caches lines homed on the other die in its own L2 after first touch; re-reads run at the local-L2 rate until one die working set exceeds its L2, then fall to the die-to-die link rate. Repeatedly-read data (KV, keys, logits) needs no die-homing if per-die working sets fit; streamed-once data (weights, KDA state) does.
- 2026-11-18 Toolchain: block-scaled MMA on sm_107 has no M64 shape (M128 / 2-CTA M256 only); non-scaled FP8 MMA has the Rubin double-K form; TMEM load-with-reduce (row max/min) is sm_107-only; counted TMA stores are not exposed in CUDA 13.4 PTX; async release multicast stores and bulk multicast copy/reduce are.
- 2026-11-18 Toolchain pitfalls: nvcc -arch=sm_107a also emits a non-arch-specific PTX pass that rejects arch-specific instructions (use explicit -gencode arch=compute_107a,code=sm_107a); arch-specific sm_100a cubins do not run on VR200; the K3.1 image ships no ncu/nsys.
- 2026-11-18 Measured (tcgen05 issue-rate probe): shared-memory operand fetch caps a 1-CTA MMA with both operands in shared memory at two thirds of the Rubin double-K peak (FP8 and NVFP4); with the A operand in TMEM a 1-CTA NVFP4 MMA reaches the full FP4 peak, and 2-CTA M256 tiles also avoid the cap. M64 instructions run at half throughput. Non-scaled FP8 double-K uses a different descriptor bit than block-scaled FP8 (documented in hwdb topic 01). Mixed FP8 x FP4 never exceeds the FP8 rate.
- 2026-11-18 Measured (4-GPU NVLink probe): a multicast store has the same one-way latency as a unicast store; a sequence of system-scope release stores to several peers serialises on full NVLink round trips (a 4-GPU flag round is about 3x slower than one multicast release store). Publish once by multicast, or fence once and use relaxed stores.
