# HW findings (public-safe: features only, no internal numbers; details in the private hwdb)

- 2026-11-18 Mixed MXFP8-activation x MXFP4-weight block-scaled MMA runs at the FP8 tensor rate on VR200; only FP4 x FP4 (NVFP4 or MXFP4 W4A4) reaches the FP4 rate. The NVFP4 checkpoint's routed experts can use it; the in-tree W4A8 MegaMoE path cannot. Matters for compute-bound prefill MoE, not for weight-bound decode.
- 2026-11-18 The Rubin double-K block-scaled MMA forms are selected by instruction-descriptor bits and only exist in sm_107a builds; family/sm_100f builds run the Blackwell form at half the block-scaled rate. Library MXFP8 and NVFP4 GEMMs we measured must already use the native form (their measured rate exceeds the Blackwell-form ceiling).
- 2026-11-18 Model observation: decode expert rows assume die-local HBM bandwidth (a non-localized MoE kernel cannot reach model achievable); dense decode GEMM rows assume the default striped rate (die-localizing dense weights can beat model achievable).
- 2026-11-18 Model observation: the prefill indexer-score row is costed near the Blackwell-form FP8 rate; a native sm_107a kernel (FP4 x FP4 or mixed at the FP8 rate) can go below model achievable. Flagged to P-IDX.
- 2026-11-18 Counted TMA stores signal completion at the destination (byte counter), removing the producer system fence + flag; payload and counter must share one large page or the count is silently skipped.
- 2026-11-18 Cluster launch control works on sm_107a, but for small decode work static/one-shot persistent scheduling was faster in internal measurements.
- 2026-11-18 Measured (Rhea): die-local HBM read is about 1.44x the default striped allocation and about 7% above the perf model die-local achievable rate (model is conservative for die-localized streams); all-remote is about half of striped.
- 2026-11-18 Measured: FP32 packed FMA (f32x2) has the same peak as scalar FFMA - it halves instruction count only; legacy warp-level BF16 mma.sync runs at one quarter of the tcgen05 BF16 rate (recurrences on mma.sync are capped there).
- 2026-11-18 Measured: a VR200 die caches lines homed on the other die in its own L2 after first touch; re-reads run at the local-L2 rate until one die working set exceeds its L2, then fall to the die-to-die link rate. Repeatedly-read data (KV, keys, logits) needs no die-homing if per-die working sets fit; streamed-once data (weights, KDA state) does.
- 2026-11-18 Toolchain: block-scaled MMA on sm_107 has no M64 shape (M128 / 2-CTA M256 only); non-scaled FP8 MMA has the Rubin double-K form; TMEM load-with-reduce (row max/min) is sm_107-only; counted TMA stores are not exposed in CUDA 13.4 PTX; async release multicast stores and bulk multicast copy/reduce are.
- 2026-11-18 Toolchain pitfalls: nvcc -arch=sm_107a also emits a non-arch-specific PTX pass that rejects arch-specific instructions (use explicit -gencode arch=compute_107a,code=sm_107a); arch-specific sm_100a cubins do not run on VR200; the K3.1 image ships no ncu/nsys.
- 2026-11-18 Measured (tcgen05 issue-rate probe): shared-memory operand fetch caps a 1-CTA MMA with both operands in shared memory at two thirds of the Rubin double-K peak (FP8 and NVFP4); with the A operand in TMEM a 1-CTA NVFP4 MMA reaches the full FP4 peak, and 2-CTA M256 tiles also avoid the cap. M64 instructions run at half throughput. Non-scaled FP8 double-K uses a different descriptor bit than block-scaled FP8 (documented in hwdb topic 01). Mixed FP8 x FP4 never exceeds the FP8 rate.
- 2026-11-18 Measured (4-GPU NVLink probe): a multicast store has the same one-way latency as a unicast store; a sequence of system-scope release stores to several peers serialises on full NVLink round trips (a 4-GPU flag round is about 3x slower than one multicast release store). Publish once by multicast, or fence once and use relaxed stores.
- 2026-11-18 Die-locality how-to published (private hwdb topics/die-locality-howto.md): allocation (VMM locality domain, torch LocalizedAllocator pools), SM->die map, die-matched claim patterns, validation, pitfalls, per-family recipe.
- 2026-11-18 Measured (full 212-SM map): each die has 106 SMs (12 SMs outside the green-context splits, 6 per die; the pair rule die = (smid>>1)&1 held on two nodes). Fine-grained placement is free: one VA range with alternating 2 MiB die chunks plus a die-matched claim reads at the die-local rate; the same range with a die-oblivious claim reads at the striped rate (placement alone gains nothing).
- 2026-11-18 Measured: per-SM HBM read throughput is capped (linear scaling with SMs up to ~3/4 of a die), so a die-local stream needs essentially every SM of the die; one die alone gets half the chip rate (dies independent); pure writes gain nothing from locality, copies gain about 1.2x.
- 2026-11-18 Measured: CUDA graph capture works with localized VMM memory; torch in the K3.1 image has LocalizedAllocator and its per-die MemPool homes tensors on the requested die, including allocations made inside graph capture with that pool. No launch-cost penalty from creating/destroying green contexts was observed with empty kernels.
- 2026-11-18 Measured: KV-row gathers must not use one 1D bulk copy per row (op-rate bound, about 12x slower than warp loads from L2 and 6x from HBM); TMA gather4 is about 3.5x better than per-row bulk but still below warp loads.
- 2026-11-18 Measured (important for every weight-streaming kernel): a TMA ring issued by ONE thread per SM with 16 KiB boxes (tensor or 1D) is capped at well under half the die-local HBM rate, independent of stage count; 64 KiB ops, or 2-4 independent issuing CTAs per SM, reach the full die-local rate. Follow-up probe (producer/consumer warp split, multiple producer warps) running.
- 2026-11-18 Measured (hw8): TMA streaming throughput per SM scales with the number of independent issuing warps (and op size), not with ring depth. The standard GEMM form (one TMA producer warp, 16 KiB boxes) reaches only ~0.6x of the die-local HBM rate for striped AND die-local memory alike - die-localizing such a kernel gains nothing. Two producer warps (or 2 CTAs/SM) reach ~0.95x of die-local, four ~0.97x; 64 KiB ops from one producer ~0.98x. Weight-stream owners (D-GEMM, D-MOE, P-GEMM, P-MOE) must check issuing warps x op bytes. TMA gathers likewise scale with issuing warps (gather4 from 16 warps gets within ~20% of warp loads from HBM).
- 2026-11-18 Measured (hw9): TMA ring throughput per issuing thread is bytes-per-stage / ~0.37 us regardless of ring depth (single 16 KiB op latency ~0.27 us from L2, ~0.6 us from HBM; ops sharing one barrier pipeline). Rule for weight streams: >= 32 KiB per stage per issuing thread, or >= 2 issuing threads, to reach die-local rate. The MegaMoE weight operand (one TMA warp, 8-16 KiB per stage per CTA) is, by this rule, issue-capped well below the die-local rate the model assumes - flagged to D-MOE/P-MOE with fixes. Per-die SM split differs per part (106/106 on one node, 108/104 on another): build the map per device.
- 2026-11-18 Measured (hw10, MegaMoE-like stage structure): with the NVFP4 tile shape (K 256 per stage) the weight stream reaches ~93% of the die-local ceiling; with the MXFP4 tile shape (K 128) it is capped at ~half for any placement. On the NVFP4 basis the MegaMoE weight-issue structure is a minor (~7%) term; K-128 tiles must not be used for decode weight streaming.
- 2026-11-18 Measured (hw11): per-SM HBM read capacity depends on the load form: 256-bit global loads give the highest register-path rate (about 1.3x 128-bit loads per SM, and the best full-chip die-local rate); multi-issuer TMA is similar; Ampere-style cp.async 16 B streams at under half the chip HBM rate and must not be used for streaming on VR200. With a high-capacity form a die saturates with about half its SMs (corrects the earlier "every SM must stream" note, which was specific to 128-bit loads with atomic claims).
- 2026-11-18 Measured (2-CTA MMA probe): cta_group::2 M256 block-scaled and FP8 MMAs with both operands in shared memory reach ~95% of the Rubin double-K peak only at N = 256; at N = 128 they fall to ~2/3 (shared-memory operand fetch bound, same model as 1-CTA). BF16 runs at full rate at both N. Compute-bound prefill GEMM/MoE tiles should be 2-CTA M256 x N256 (or 1-CTA with A in TMEM); the MegaMoE prefill tile (N128) sits at the ~2/3 point.
- 2026-11-18 Measured: TMEM loads run ~1.5x faster than stores and improve ~1.35x when several tcgen05.ld are issued before one wait; batch TMEM loads in softmax/state/epilogue loops (hwdb topic 02).
- 2026-11-18 Measured (hw12): HBM writes hit the same ceiling for every store path and placement (no locality gain); in-place read+write state updates gain ~1.22x from die-local placement; TMA bulk reduce-add into global runs at about half the write rate. A third node showed yet another per-die SM split, so per-die work must be balanced from the measured map.
- 2026-11-18 Measured (hw13): TMA producer warps on distinct vs the same SM subpartition differ by at most ~4%; the number of issuing warps (or op size) sets the per-SM TMA stream rate. Supersedes the "distinct warp_id % 4" advice.
- 2026-11-18 Measured (hw14): tcgen05.mma can be issued from two warps of one CTA at full rate (one in-order MMA pipe per SM); a commit waits for every MMA already in the pipe, including other warps' MMAs; the issuing thread is back-pressured after ~5 queued MMAs; each commit -> barrier wait -> issue handoff costs ~300-400 clk. A split QK/PV issue design is legal; a hang there is a barrier/phase bug.
- 2026-11-18 Measured (hw13/hw13b): cluster multicast TMA loads (1D bulk or tensor) deliver at the same rate as plain loads; what made multicast slow in a single-thread ring was the per-stage cross-CTA slot-release handshake (plain loads with the same handshake are equally slow, ~0.5x). Multicast needs a separate producer warp, a deep ring and the empty wait off the issue path; otherwise duplicate L2 loads are as fast.
