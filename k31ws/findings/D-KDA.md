# D-KDA findings (decode KDA core, FP32 state)

- 2026-11-18 Production coverage (rhea1n spgemm-prof agentx.log): records mode "deferred"; KdaWide (folds the pending commit itself) at n <= 70 requests per DP group, KdaWS above (does NOT fold: the step's first KDA core flushes every layer's pending commit with a separate state read + write pass, then KdaWS reads the state again).
- 2026-11-18 Model target per layer (rhea1n/model_rows.json, kda_core = conv + gate_beta_norm + core_decode + o_norm): B32 8.76 us, B64 17.5 us, B96 26.3 us; memory bound at the measured full-chip HBM rate on 64 KB state read + 64 KB write per (request, head) item. In-step measured (rhea1n_d3x32 93L): 21.5 / 38.5 / 49.2 us per layer.
- 2026-11-18 Model note (not an error yet): FP32 recurrence + fold is ~0.8 MFLOP per item, ~55-60% of the memory time at the model's HBM rate; the model's max(compute, memory) assumes perfect overlap of the FP32 pipe with the state stream.
- 2026-11-18 Microbench (runs/D-KDA/run2.log, 1 GPU, 69 layers / disjoint slots, deferred fold active, us/layer): KdaWide n8/32/64/96/128 = 8.6/26.0/51.5/74.3/95.0; KdaWS (no fold, flush NOT included) = 11.6/20.5/37.4/48.5/62.3; KdaFlow (WS + fold) 1-stage = 11.8/32.9/53.5/71.7/93.4, 2-stage no better. State R+W stream only 3-6.5 TB/s: NOT bandwidth or bytes-in-flight bound (2-stage ring gives nothing). Per-item latency ~8.5-12 us (n8, one wave). Fold costs +12 us/layer at n32 inside the WS structure. No ncu/nsys in the image: diagnosing with in-kernel clock64 traces.
- 2026-11-18 KdaFlow (KdaWS + in-kernel deferred fold) is bitwise equal to KdaWS triton + the stock Triton commit (16/16 tests, eager + graph, n3/33/96/128). But it is slower than KdaWide at n<=64 and only ~par with KdaWide at n96.
- 2026-11-18 Cost attribution of KdaFlow v2 by leaving parts out (runs/D-KDA/run5.log, us/layer n32 / n96): full 38.0 / 91.7; no fold 24.1 / 48.5; no verify 20.6 / 49.5; neither 14.1 / 32.0; no fold store 29.6 / 92.2. Fold and verify each cost ~43 us at n96 (~9K cycles/item each vs ~1-2K instruction floor) -> pathological scan code (suspect register cap / local memory: cuobjdump shows KdaFlow REG 128 + STACK 88, KdaWS/KdaWide STACK 0). Prep + state load floor alone is 32 us at n96 (~7K cycles/item with 2 prep warpgroups) -> above the 26.3 us model target by itself: prep must be restructured too.
- 2026-11-18 v2 changes (fused token passes, staged F_B/records, head-major items) did not help (n96 91.7 vs v1 71.7); fold-free KdaFlow == KdaWS (48.5) confirms the verify path is unchanged in cost.
- 2026-11-18 ptxas -v: KdaFlow 128 regs + 104 B spill stores / 96 B spill loads (KdaWS, KdaWide: none). But the scan/prep setmaxnreg split (168/88, 152/104, 184/72, 136/120) does not change n32 time (37.9-38.0 us) and only worsens n96: spills are NOT the main cost (runs/D-KDA/run6.log). Root cause of the ~9K cycles/item fold and verify still open; needs SASS (nvdisasm missing in the image) or ncu (missing).
- 2026-11-18 Tooling blocker: the K3.1 image has ptxas + cuobjdump but no nvdisasm, ncu or nsys, so SASS and stall reasons cannot be inspected on Rhea.
- 2026-11-18 (resumed) Hang root cause in KdaFlow v3: warps reached aligned barriers (bar.sync, setmaxnreg, mma.sync) diverged after single-lane mbarrier waits; warp convergence (bar.warp.sync) before every aligned op fixed it.
- 2026-11-18 n96 cost isolation (KdaFlow v4, 24-layer microbench, us/layer): page reads alone 15.3-15.8 (~9.6 TB/s read), + checkpoint stores from registers (STG) +20.5, + prep +14, + verify FP passes +12, + 8-lane row reductions/broadcasts (22 shuffles per token) +24, + fold +12. Setmaxnreg register splits change nothing; a fold whose independent chunks let ptxas hoist loads spills even at 255 registers (a warp sync per chunk removes it).
- 2026-11-18 Synchronous global accesses inside the item loop (L2 loads of F_B fragments, record stores) cost ~8K cycles per item under the saturated state stream (v5 trace); moving every per-item global access to bulk copies (inputs one item ahead on an mbarrier, outputs from smem) cut n96 from 86.6 to 64.6 us/layer (v6).
- 2026-11-18 Shared-memory return path bound: an LDS.128 warp instruction costs 4 cycles of the 128 B/clk path even when all lanes broadcast. A thread layout must reuse each loaded 4-key vector chunk over many rows: 2 rows/thread (pair/half layouts) ~7.4K smem cycles per item vs ~3K at 8 rows/thread. v8 (8 rows x 16 keys, async framework): n32/64/96/128 = 21.6/38.0/53.1/70.6 us/layer.
- 2026-11-18 Tool: SASS opcode histograms without nvdisasm: compile the kernel PTX with the image ptxas in the colima VM and classify 128-bit words by the low 12 bits against an opcode table built from PTX probes (~/.cache/k31ws-ptxas/dkda/sassop.py). FFMA2 0x249, FMUL2 0x24a, LDS 0x984, STS 0x388, MOV 0x202, HMMA 0x23c, MUFU 0x308, SHFL 0xf89 (likely).
- 2026-11-18 HYPOTHESIS (INFRA to check): the step-slice baseline (KdaWS 49.2 us/layer at r24) contains no flush/commit kernel -> it likely runs with pending = 0 (no RecoverSSM fold, no state write). Production deferred mode pays a fold pass per layer; compare cores with pending > 0.
- 2026-11-18 setmaxnreg does not buy registers for a scan warpgroup next to a prep warpgroup here: ptxas compiles the kernel at the 168-register launch cap (384 threads); the scan code loses ILP (verify 11-14K vs 7.4K cycles/item). Keep 256 threads x 255 registers.
