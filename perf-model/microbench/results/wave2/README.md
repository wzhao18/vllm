# Microbench wave 2: EP32 scale-out and wave-1 gaps (2026-11-18)

Rows: `rows.json` (wave-1 schema, plus `moe_kernel` and `wave`), regenerated by `python3 mkrows.py`. Same harnesses,
env, tree and image as wave 1 (reuse rule). Nothing new was built, except a derived-config script and a pair-task
wrapper. Both are described below.

- **Code.** Release tree `rel-1767cf7` (6a14e2fada), FlashInfer 0.7.3.dev20261031, dummy weights, real K3.1-Pro config view.
- **MoE kernel.** Every MoE is the vLLM-vendored MegaMoE (`megamoe_rubin`), labelled `moe_kernel=vendored`.
- **Model.** `t_ach`/`t_sol` come from the current `out/optables.json` (prefill F16384 L78K). For P4 (f_req 4096) and
  D3 (exact r), the current model code is evaluated at the exact measured shape inside `mkrows.py`.
- **Model drift warning.** `out/optables.json` was regenerated at 07:31 EST today, while wave 2 was running (meta
  `generated 2026-11-18 07:31`). Wave-1 rows and RESULTS.md use the older tables: for example P3-16 F16K was 960.4 ms
  and is now 838.7; D3 r8 was 14.70 ms and is now 13.86. Wave-2 derates are against the new tables, so they are not
  directly comparable with the wave-1 bands.
- **Precision.** Checked in every log:
  - fp8 MLA KV, mxfp4 indexer KV, fp32 KDA state, BF16 model dtype;
  - MoE activation `float8_e4m3fn` with uint8 group-32 scales (MXFP8);
  - exact top-k (prefill `trtllm_gvr2`, decode `deep_select`);
  - decode `decode_backend latency_specialized` only (no stock decode arm anywhere);
  - prefill MegaMoE quant kind asserted from `Rubin MegaMoE (<kind>, EPn)` / `92 layers in the <kind> kernel layout`.

- **r <= 32 is a hard code limit.** The specialized decode refuses SP above 512 verify rows (max_num_seqs x q): r48

  `_capture_and_time`): 245 GiB allocated plus 10.4 GiB reserved. This is the same bench artifact as wave-1 D3 B128.

## Failures and root causes

1. **P3-32 (DEP32) cannot start on the release tree.** Every rank raises at load:

   ```
   KnobLookupError: no knob record for variant=inference dtype=mxfp4_mxfp8 world_size=32 max_tokens=16384
   ```

   - It fails the same way at max_tokens 8192, and for `dtype=nvfp4` (the release arms).
   - Code: `vllm/models/kimi_k3/nvidia/megamoe_rubin/config.py:659` `resolve_knobs`, called from `make_buckets` (line 910).
   - The shipped knob table for `kimi_k3_mega_moe` has records only for world_size 4, 8 and 16. The bench has no EP
     whitelist, but the knob table acts as one at EP32.
   - Not worked around. The options are a tuned EP32 knob record, or a different MoE backend (for example
     `deep_gemm_mega_moe`, which D3-32 runs at EP32). The second option is not like-for-like with P3-16.
   - Logs: `$W/mb/prefill/results/w2p332/p332_{mx16,mx8,rel16,rel8}.log`.
2. **D3-32 r48:** refused by the SP 512-verify-row cap (see above). **D3-32 r32:** bench capture OOM.
3. **D1 NVFP4 arm: not run.** No release arm exists. The release D1 decode role (`dsrel-c48-1p1d-xdr`) uses
   `moe-backend auto`, which is the specialized decode's own MoE with MXFP8 activations, identical to wave-1 D1.
   NVFP4 MoE in the specialized D1 path would be a new code path, not a release arm.
