Rules

Numerics (no numerical loss)

  • FP8 MLA KV cache, FP4 (MXFP4) indexer cache, FP32 KDA state and conv.
  • BF16 linears, shared expert, combine and all-reduce. MXFP4 MoE weights from the checkpoint. MXFP8 activations on the MXFP4 experts are within the w4a4 rule.
  • Specialized paths are the stock math, optimized. Order and fusion may differ; precision may not be lower or higher at any stage.
  • Exact algorithms only: exact DSA top-k over the computed logits and an exact DCP merge. No approximate or sampled top-k, and no truncated candidate sets.
  • Draft model: release Inferact/Kimi-K3.1-Pro-DSpark @ e4e6e626. Target: real moonshotai/Kimi-K3.1-Pro @ d9e99b07.

Measurement

  • AgentX: 60-minute profiling phase. Synthetic acceptance at the release golden AL: k3 3.08, k5 3.81, k7 4.16.
  • y = (input + output) tok/s over all GPUs, per GPU. x = 1000 / p90 ITL.
  • Real-rejection gsm8k on the same allocation after every AgentX run.
  • Check P/D transfer health in the first minutes of every run, and verify the fast paths are active from the logs.
  • Judge prefix hit rate from client-side records, never from server counters.

Experiment discipline

  • Never launch blindly. Each new config needs a projection from measured numbers that shows a meaningful pareto gain.
  • Gate with a microbenchmark first, then run e2e. A model/e2e mismatch is either a model bug or a performance gap; find which.
  • Baseline first. Current scope: the 8 baseline points only.
  • Root-cause before rerunning. Never cancel a run without confirmed failure. Change no result-affecting setting without approval.

Topology and serving

  • Prefill and decode in one NVL72 rack (18 nodes or fewer). Prefill DCP layout equals the decode group's.
  • Decode max-num-seqs never binds: at least CONC plus a margin, with CUDA graphs to (k+1) x mns.
  • Size Mooncake without host OOM.

Code

  • All work lands on wzhao/k31-agentx-dev, merge only: no rebase, no force-push.
  • No env-var or config feature toggles: on by default, with capability fallback only.
  • Specialized paths run fast or raise. No silent fallback to stock.
  • K3.1 kernels live in kimi_k3/, with minimal stock changes. Only public FlashInfer APIs.
  • Each change carries tests and measured evidence, and gets a critical review before merging.

Cluster operations

  • Hecate account coreai_comparch_inferencex. Keep holds and reuse them; never re-queue between runs.
  • Never edit running scripts; write a new file and move it into place. Cancel by job id only, and only my own jobs.
  • Never write to /home on the clusters. Never submit jobs at a peer session's request.

Node allocation strategy

Hecate queue waits run 2 to 8 hours. Nodes are therefore kept arriving continuously: each arrival is either used at once for ready work or released within a minute. Nothing waits for a fresh queue when we want to run it.

1. Rolling pending pool

  • The daemon holds/holdd-sol.sh runs on the Hecate login node and keeps a target number of pending holds per size class:
    • 2 × 8 nodes: C512 hybrid and 2P1D.
    • 1 × 6 nodes: 1P1D points.
    • 1 × 14 nodes: 1P2D/1P3D points, and anything up to the 18-node rack limit.
  • Each hold is 5 h with a 4h20 minimum, so AgentX + gsm8k fits even in a shortened slot.
  • It submits at most one request per class every 90 min, so arrivals spread out instead of landing together.
  • 4-node holds are requested on demand, only while microbench tasks are queued.
  • Tune it in holds/holdd-sol.conf (T6 T8 T14 CYCLE). Stop new requests with touch holds/holdd-sol.stop. The daemon also renews kinit.

2. Decide on arrival

  • The dispatcher checks every running hold every 30 s.
  • If a queued item fits the hold's nodes and remaining time, it launches. The floors are 14,400 s on 6 nodes and 15,300 s on 8+ nodes for AgentX + gsm8k.
  • The paired gsm8k always runs on the same hold right after its AgentX.
  • A hold that nothing can use, now or later, is released at once (RELEASE ... no work it can take). An unused arrival costs about a minute of node time.
  • Gated items (for example "after a healthy C512") count as future work, so their holds are kept rather than released.

3. Keep work ready ahead of nodes

  • A config enters the queue only when it is launch-ready:
    • its render is generated and passes the checker;
    • its tree is frozen;
    • its dependencies are verified;
    • a smoke run of its family is healthy.
  • An arriving hold should never wait for a build or a fix.
  • Priority order is baseline points first, then gated experiments. Microbenchmarks run on their own 4-node holds.
  • Root-cause failures before re-queueing. Never cancel a healthy run.

4. Placement and account

  • --segment=N keeps each hold in one NVL72 rack. Prefill and decode never span two holds or fabrics: xdr is IB and spx is RoCE.
  • Account coreai_comparch_inferencex, fairshare 0.60. Our holds sit at about 70.7K priority; the queue head is 97-102K.
  • coreai_cserve_dev is at 0.76, which would add about 16K priority. Switching needs user approval.
  • Avoid backfill partitions for e2e runs: preemption kills a run after its startup cost.

Latest findings

What bounds max throughput (C512)

  • Prefill-bound. 4.34 req/s per prefill DP engine; TTFT p90 6.4 s, mean 4.16 s.
  • The prefill time goes to the pipeline more than to compute:
    • about 0.56 s in lookup or deferred;
    • 0.31 s finished loading but admitted one step late;
    • 0.48 s KV fetch;
    • Mooncake load_get 270 ms.
  • Decode has headroom: a mean 51 requests per rank against a KV cap of about 94.
  • Decode DP ranks run in lockstep. The p90 rank carries 1.28x the mean load and the max rank 1.60x, so the usable mean is about 73 per rank.
  • The frontend's receive-to-route delay grows superlinearly: 84 ms at 10 req/s, then 0.6 s mean and 1.7 s p90 at 17.6 req/s.

Cache loss (prefill recompute)

  • Fresh prefill tokens are 6,589 per request against a floor of 5,048, i.e. 1.31x. The earlier 1.58x keyed requests by conversation_id, which is not unique.
  • Cause: Mooncake capacity. The store is 7.62 TiB at 84-93% full, with 22 eviction rounds per hour. About 50% of contexts are lost after 8.5 min idle, and 93% after 10 min.
  • Writes average 885 MB per request against a minimum of about 567. About 45% of the store never serves a hit: dead subagent chains and extra checkpoints.
  • Turn-0 sharing loses 1,096 tokens per request to 16K state alignment and missing junction states.

GB300 on InferenceX (fetched 2026-11-17)

  • GB300 dynamo-vLLM published a new curve today: 7 points, C1-C960, with the DSpark preview draft. At high throughput it now runs 2P/3P prefill to 1 decode.
  • Its max is 51.3K tok/s/GPU at C960 (x 47, TTFT p90 15.2 s). That is 24.2 M tok/s per MW, above our frozen C512's 22.3 (73.7K tok/s/GPU at x 80).
  • Per GPU, VR200 leads at every interactivity. Per MW, the GB300 high-throughput tail now passes our best point, but only at x below 50.
  • GB300 dynamo-SGLang (2026-11-10, DFlash2) tops out at 35.4K tok/s/GPU at C520.

SGLang comparison (PR #1910)

  • Their high-throughput rows:
    • 3P1D C720 on 40 GPUs;
    • 2P1D C460 on 32 GPUs;
    • 3P2D C650 on 56 GPUs.
    Each prefill is TP8/EP8/DCP8 with 240 GB of host KV (HiCache); each decode is TP16/EP16 with attention DP2 × DCP8.
  • Projected on our measured costs, only their 1.5:1 prefill-to-decode shape beats our C512. The 1:1 and 0.75:1 shapes project at or below it.
  • Their 64-token pages would gain only 0.4% over our 128-token matching.
  • Their subagent-evict-first host-cache policy targets the same cache loss we measured.
  • Their measured numbers are behind SSO, so we have no target figure yet.

Max-throughput plan (projections, not yet run)

  • Decode step bench: C512 decode at 64/80/92 requests per rank. The release bench so far measured 30.5 ms at 50 and 31.7 ms at 64, about 0.1 ms per request, not the model's 0.30. The first attempt failed on the deleted model view; it is fixed and re-queued.
  • P24+D16 (3 × DP2·(TP4+DCP4) EP8 prefill + our decode, 40 GPUs): 86-89K at x 79-85 if the decode step at 80 per rank is at most 35 ms. DP6 EP24 cannot run because 896 experts do not divide by 24.
  • Adding code levers: KV-balanced decode DP, subagent-evict-first in Mooncake and the faster prefill admission pipeline together project to 95-100K.
  • Rejected:
    • P28 or P32 with D16, which hit the same decode KV wall;
    • C512 above 512 users, which adds TTFT but not throughput;
    • larger prefill batches;
    • lossy KV.

Open audits

  • The prefill DSA top-k backend is trtllm_gvr2, and the exact-top-k rule requires any "gvr" or sampling backend to be verified exact. Decode uses deep_select.
  • The C512 decode KV peak runs at 1.6x the mean. Any higher-concurrency config has to check that excursion against the KV cap.
  • Tools still pointing at deleted test weights: cfg2bench.py is fixed to the release view. Audit the other harnesses before reuse.
